# 64×4/128×8 从零训练性能校准记录（2026-08-30）

目的：为 128×8 从零训练选定最能释放吞吐的 `num_workers` / `file_batch_size`
组合，并记录性能瓶颈的定量分析。方法：校准配置由主配置逐臂参数替换生成
（`save_every=400`、`max_steps=400`、独立 state 路径），经
`scripts/run_config.ps1` 启动，矩阵完成后已移除。

## 瓶颈分析（为什么 GPU 利用率低是结构性的）

| 架构 | Brain 参数量 | 相对 32×2 参数 | 相对 32×2 单样本 FLOPs |
|---|---:|---:|---:|
| 32×2（现冠军血统） | 1,205,572 | 1.00× | 1× |
| 64×4 | 1,371,888 | 1.14× | ~8× |
| 128×4 | 1,829,312 | 1.52× | ~32× |
| **128×8（本实验）** | **2,233,312** | **1.85×** | **~64×** |

参数量被固定输出头（Linear 1088→1024 ≈ 111 万）主导，通道/块数扩张的参数
收益递减。FLOPs 增长远快于参数。**实测（128×8，workers=6）：稳态 2.64 步/秒
（2,703 样本/秒），GPU 利用率仅 ~10%**——即使 FLOPs 放大 64 倍，墙钟瓶颈仍
在观测编码管线（gzip + libriichi3p 重放，容量 ~2,600–2,700 样本/秒），
训练循环以突发方式消化批次后等待下一块编码。tqdm 的脉冲模式（1–6 batch/s
振荡）是管线限制的直接证据。

结论：**吞吐调优的对象是数据管线参数，不是 GPU 参数**；加大 batch_size 在
管线封顶下不改变每 epoch 墙钟时间，反而改变预注册实验的优化动态，不采用。

## 校准方法

- 每臂 400 步独立运行（校准配置：`save_every=400`、`test_every=100000`、
  `snapshot_every=0`，独立 state 路径）；
- 稳态速率取 tqdm 日志中 step 101→299 的累计耗时差（自动排除启动开销：
  worker spawn、MIOpen 编译、file index、首批编码）；
- MIOpen 内核缓存与 64x4 file index 在首臂建立，后续各臂复用；
- 硬件：RX 9070 XT，batch 1024，ROCm 7.2.1。

## 校准矩阵（batch 1024，128×8 架构，同批串行运行）

| 组 | num_workers | file_batch_size | 稳态步速 | 样本吞吐 | 相对最优 |
|---|---:|---:|---:|---:|---:|
| A | 6 | 8 | 3.33 步/秒 | 3,413 /s | −10% |
| **B（胜者）** | **8** | **8** | **3.70 步/秒** | **3,793 /s** | — |
| C | 6 | 16 | 2.71 步/秒 | 2,777 /s | −27% |
| D | 8 | 16 | 2.69 步/秒 | 2,754 /s | −27% |

## 结论与采纳

- **胜者：`num_workers = 8` + `file_batch_size = 8`（3,793 样本/秒）**，比
  32×2 冠军时代的 ~2,600 样本/秒快 46%；
- 意外发现 1：`file_batch_size = 16` 反而全面劣于 8——更大块使单次编码停顿
  加倍，超过 DataLoader 预取（prefetch_factor=2）的缓冲能力，管线出现空窗；
- 意外发现 2：`num_workers = 8` 在 128×8 下反超 6（+11%），与 32×2 时代
  "6 优于 8"的结论相反——主循环每步计算更重后，CPU 争夺格局反转，主进程
  从 worker 手里让出的核由更长的 GPU 步时间补偿；
- 已采纳：`Mortal/config/sanma-training-128x8.toml`（架构 128×8、workers 8、
  file_batch 8、46,500 步 ≈ 1 epoch ≈ 3.5 小时）；
- epoch 墙钟时间受管线封顶约束的结论不变：GPU 利用率仍然不是本负载的健康
  指标，样本吞吐才是。

## 已知边界

- 天凤单会话规则约束的是下载并发，与本训练吞吐无关；
- 观测编码缓存不可行（全语料编码 ≈ 1.2TB，见 round-2 报告）；
- 若未来需要进一步突破 ~2,700 样本/秒，路径是 Rust 原生 v4 编码器
  （消灭 Python 逐事件重放，预估 3–8×），见性能路线图讨论。

## 事故记录（22:16，128×8 首次运行）

训练期间并行执行了 CPU 密集的差分验证与 CPU 冒烟测试，8 核机器上训练的
8 个 DataLoader worker 与主进程已饱和，附加负载导致 worker 进程被系统终止
（`DataLoader worker exited unexpectedly`），训练在 24,000 步存档后崩溃。
状态文件完好，从 24,000 步恢复并顺带激活 orjson 与 val loss（即计划的
重启测速点）。**规则：训练运行期间禁止执行任何 CPU 密集的并行任务。**

## orjson 上线后的实测 A/B（23:15–23:19，128×8 同一运行轨迹）

- 崩溃前（旧代码）：3.05–3.48 步/秒（3,120–3,560 样本/秒，含启动摊销）；
- orjson + val loss 重启后：存档到存档 3.75 步/秒（3,840 样本/秒，**含**每
  2,000 步一次的 val 评估开销）；扣除 val 后训练纯速率 ~4.2 步/秒
  （~4,300 样本/秒）；
- **端到端提升 +20–35%**，与"JSON 占编码成本一部分"的预估一致；批次突发
  从 3–6 batch/s 升至 4.3–9.4 batch/s；
- val 评估（每次 ~30 秒，含 worker 孵化）在 2,000 步间隔下摊销 **~6%**
  （30s / (2000/4.2)s）——用户正确指出这不小。第 1 epoch 内过拟合风险本身
  极低（26k 处 train≈val=0.441/0.442 已实证），故 val 对本次运行属确认性
  冗余、非必需（且中途关闭需重启，不值得）；**第 2 epoch 扩展时**过拟合
  风险实质化，val 上岗，建议 `val_loss_every=4000` + `val_max_batches=25`
  把开销压到 ~1.5%，或将验证改为常驻 val loader（省去每次 8 worker 孵化
  的 ~10–15 秒）。

## 事故复盘（22:16 崩溃与两次挂起）

1. **worker 被杀**：训练期间并行运行 CPU 密集的差分验证与冒烟测试，8 核
   饱和下 DataLoader worker 被终止 → 训练崩溃于 24,000 步存档后。规则：
   **训练运行期间禁止并行 CPU 密集任务**；
2. **旧进程假死**：崩溃进程打印 traceback 后未退出——非守护线程卡在解释器
   关闭阶段，持续空转（CPU 计时 >6,600s）且状态文件不再更新；
3. **新进程孵化挂死**：在旧进程残留的污染环境下重启，新进程 8 个 worker 未
   孵化完成即挂死（CPU 空转、零内存增长）；
4. **解法**：TaskStop 终止全部相关任务树 + taskkill 清理残留进程后第三次
   启动，一次成功。**操作规则：训练异常后，先整树清理再重启，不叠加重启。**

## val 开销评估与吞吐路线图（23:2x 补充）

- val（每 2,000 步 ~30 秒）摊销 ~6%，本次运行剩余部分合计 ~5 分钟。第 1
  epoch 内过拟合风险本身极低（模型尚未看完全部数据，26k 处 train≈val=
  0.441/0.442 已证实），故 val 对**本次**运行非必需；其真正岗位是第 2 epoch
  扩展（过拟合风险实质化，val 拐点 = 最便宜的停止信号）；
- 吞吐瓶颈确认仍在编码管线（4,300 样本/秒，GPU 5–10%）。路线图：
  orjson +30%（已上线）→ **metadata-only + 事件准备复用（本轮已上线）**
  → worker 内多游戏线程并行（Rust 调用释放 GIL，中等工程，可选）→
  Rust 原生 v4 编码器（目标 3–8×，仍需 ABI 差分验证）。
- 本轮安全优化：compat 训练仍以历史 v4 pyd 生成 775×34 观测，但 Rust
  `GameplayLoader` 不再生成随后被丢弃的 v5 obs/mask；同一文件的三麻→四席
  JSON 事件适配也只做一次。Rust 34 项 sanma 单测通过，Python
  `compat_failure_recovery_check.py` 通过。
- 严格端到端基准（同一批 8 文件/24 游戏/2,760 样本，reference capture 与
  事件准备完全相同）结果：raw **959.5 → 1,068.6 samples/s（+11.38%）**；
  增广 **963.7 → 1,066.7 samples/s（+10.68%）**。样本数和游戏数完全一致。
- raw 与增广模式的旧/新 reference capture 在真实样本上逐元素 obs/mask 一致；
  `checks/compat_loader_benchmark.py` 可复现上述两臂结果。
  旧扩展会自动回退到 full metadata pass，避免二进制未更新时破坏训练。
- native v4 不能在本轮直接启用：当前统一分支原生 v4 ABI 曾出现 780→775
  行数断言问题，且与历史 775 输出存在多处布局差异；已保留为下一项独立
  工程，须先复原完整 row map 并通过 golden parity，再切训练默认路径。
- 注意：即使编码器 8×，GPU 仍只 ~3% 峰值算力——吞吐扩建收益是纯时间收益，
  不会撞 GPU 墙；加大 batch_size 在管线封顶下永远不划算，该判断链闭合。

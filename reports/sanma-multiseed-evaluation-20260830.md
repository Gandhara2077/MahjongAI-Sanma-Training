## 本轮修复与验证

失败根因是历史 `libriichi3p` v4 mask 允许 action 40（拔北），而修正后的 native sanma 规则在立直后拔北会改变等待时禁止该动作。兼容层现在在每个 worker 请求中读取 native 当前 mask，仅在 native 不允许时从历史 mask 移除 action 40；合法拔北和其它 action 不变。

验证结果：

```text
Python compat failure recovery check: PASS
three-way runner check: PASS
Python py_compile: PASS
Rust sanma tests: 33 passed, 9 ignored, 0 failed
real three-way smoke: PASS (3 games)
three-way full run: exit 0, 3000/3000 compressed logs
```

运行中出现的少量 `recovered historical nukidora furiten mismatch` 是既有恢复路径的 warning，未导致失败或丢失日志。

### 方法学教训

固定种子 300 局 test_play 曲线（16k–36k 全程 1.97–2.04）显示"平局"，而 3,000 局新种子面板显示真实水平 1.946。原因：300 局噪声 ±0.047 加上固定种子集偏移。**教训：小于 ~0.05 顺位的效应只能用数千局多种子面板判定，固定种子训练曲线不具备该灵敏度**——2e-6 的训练 loss 优势（dqn_loss 0.562 vs 0.581）确实兑换成了棋力，只是被低灵敏度仪器掩盖了大半天。

### 修订后的判定

1. **晋级 `training/sanma_lr2_mortal3p.pth`（40k）为冠军**；原始基模与全部快照保留不动。
2. 1e-6 血统按原结论保留为证据。
3. 预注册判据"明显低于 2.0 → 下一档学习率"已被触发：下一档为 peak 5e-6（约 8 小时），或按项目收尾计划就此封存。

## 方向决策：跳过 5e-6，转入 128×8 从零容量实验（2026-08-30 深夜）

5e-6 档经决策跳过：LR2（2e-6）已交付本轮收益，而容量假设提供了更大的博弈空间。**启动前修正一处规格错误**：实测参数量显示原计划的 64×4 仅 +14% 参数（1,371,888 vs 1,205,572）——架构输出头（Linear 1088→1024 ≈ 111 万）主导参数量，通道/块数扩张收益递减。容量实验因此重新规格化为：

- **128×8 从零训练**：2,233,312 参数（+85%）、随机初始化（无 `init_from`）、peak 1e-4、warmup 1000、max_grad_norm 1.0；
- 配置：`Mortal/config/sanma-training-128x8.toml`；46,500 步 ≈ 72,273 局语料的 1 epoch（训练窗口并入 08/08–08/29 增量，07/25–08/07 保留为 GRP 验证窗）；
- 吞吐调优（workers=8、file_batch=8，3,793 样本/秒）：`reports/performance-tuning-20260830.md`。

34% 进度的早期信号（step 4k/8k/12k 固定种子 test_play = 1.883 / 1.820 / 1.833，低于所有微调血统在同一集合上的 1.97–2.04；dqn_loss 0.445 vs 0.56–0.58 且行为同步改善）方向正面，但裁决以训后面板为准。两道门：

1. 全新种子 key，3,000 局 vs 原始基线（证书级判定）；
2. 共享 key 配对 vs LR2-40k 冠军（"是否强于我们最好的"）。

**预注册非对称解读**：若失败，只能得出"72k 局喂不饱 2.2M 参数从零训练"（数据饥饿），不能得出"容量无用"。

后续顺序：容量成功 → 调度延长机制扩到第 2 epoch → 重面板 → 转入在线自对弈（唯一无数据上限的轴，需先完成 automation 的两项修复：数据隔离、绝对目标步数）。容量失败 → 剩余杠杆为蒸馏（容量+先验知识）或在 32×2 冠军上直接 RL。

方法缺口（为任何续训记录）：**主模型没有 held-out 验证 loss**——全部语料都在训练窗口里。运行中段（20k 步）训练 loss 仍在下降而固定种子评估已走平，两者在 300 局噪声下无法区分"仍在上限爬升"还是"过拟合开始"。低成本修补：从语料预留 2–3% 永不训练的文件，每次 save 做 forward-only 验证 loss 评估，观察 val loss 拐点向上。停止与选模本身保持行为面板判定，不用 loss 判定。
